Operations

Everything that goes wrong after the demo works.

Deployment shape

        TLS
   ┌──────────┐        ┌────────────────────────┐
   │  Caddy   │───────►│  paisabridge (loopback) │───► SQLite file
   └──────────┘        └────────────────────────┘
        ▲                          ▲
        │                          │ webhooks (signed)
   storefront                      │
                              rails / relay

One process per SQLite file. Two processes on one file produce database is locked under load; if you need horizontal scale, run one writer per database and put a queue in front of it.

The operator console runs on its own listener (PB_ADMIN_ADDR), so it can be bound to loopback or a VPN address and never exposed on the payment port.

systemd unit

[Unit]
Description=paisabridge
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=paisa
EnvironmentFile=/etc/paisabridge/env
ExecStart=/usr/local/bin/paisabridge
Restart=always
RestartSec=3
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
NoNewPrivileges=yes
ReadWritePaths=/var/lib/paisabridge
StateDirectory=paisabridge
WorkingDirectory=/var/lib/paisabridge

[Install]
WantedBy=multi-user.target

Keep EnvironmentFile at chmod 600, owned by the service user.

Before you take real money

  1. Generated secrets, not typed ones. openssl rand -hex 32 for every rail secret and the admin token.
  2. PB_REQUIRE_SIGNATURE=true (the default). Never disable it outside a test.
  3. TLS in front. The gateway speaks plain HTTP and trusts X-Forwarded-For only when PB_TRUST_PROXY=1.
  4. Backups scheduled before the first order.
  5. Admin token in a password manager, not in shell history.
  6. Clock synchronised. Signature windows and order expiry both assume NTP.

Backups

SQLite is safe to copy live with .backup:

sqlite3 /var/lib/paisabridge/paisabridge.db \
        ".backup '/var/backups/pb-$(date +%F).db'"

Cron it daily, keep 14 days, and restore-test once:

systemctl stop paisabridge
cp /var/backups/pb-2026-01-01.db /var/lib/paisabridge/paisabridge.db
systemctl start paisabridge
curl -fsS localhost:8080/api/readyz

Monitoring

Two signals catch almost everything:

SignalMeaningAlert on
webhook_signature_failures_total risingforgery attempts, or a rotated secret on one sideany sustained rate
outbound_deadletter_open > 0your storefront webhook is down; deliveries are parked15 minutes
orders stuck in reviewbank rail waiting for a humanolder than 30 minutes

Health probes: point the load balancer at /api/readyz and the process supervisor at /api/healthz. "Take me out of rotation" and "restart me" are different decisions.

Upgrades

git fetch --tags
git checkout v0.2.0
make build
systemctl restart paisabridge

Migrations run at startup and are additive; there is no down-migration. Take a backup before every upgrade that changes one.

Capacity

Order create is two indexed inserts; a 2-vCPU box handles a few hundred per second. The real limits are the provider's webhook rate and SQLite's single writer. If you outgrow it, split rails into separate deployments — each writes its own database, and the storefront stitches the results.
