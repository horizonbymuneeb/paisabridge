API reference

JSON in, JSON out. All amounts are integer minor units — paisa for PKR (1 PKR = 100), micro-units for USDT (1 USDT = 1,000,000). No floats anywhere.

Conventions

POST /api/orders

{
  "product_id": "chatgpt-plus",
  "product_name": "ChatGPT Plus — 1 month",
  "catalog_price_minor": 149900,
  "currency": "PKR",
  "method": "easypaisa",
  "customer_email": "buyer@example.com",
  "customer_phone": "tg:123456789",
  "ttl_seconds": 900,
  "idempotency_key": "cart-8812"
}
FieldRequiredNotes
product_idyesyour catalogue key
catalog_price_minoryeslist price, > 0
currencyyesPKR or USDT
methodyeseasypaisa, jazzcash, nayapay, sadapay, bank, usdt, binance, payoneer
customer_phonenotg:<chat_id> binds the order to Telegram
ttl_secondsnodefault 900, max 3600
idempotency_keynoretry-safe creation, see below

Idempotency. Send idempotency_key when your checkout retries. The same key with the same body returns the same order with 200 instead of creating a second one; the same key with different content is 409 idempotency_conflict, because creating a duplicate silently is worse than a clear error. One key per customer intent, not per HTTP attempt — verified live: 201 then 200 with the same id.

GET /api/orders/{id}

{id} accepts the UUID or the short ref. Returns the order plus its journal:

{"order": {...}, "events": [
  {"from_status":"created","to_status":"pending_payment","actor":"system","created_at":"..."}
]}

POST /api/orders/{id}/claim · /cancel

claim pays an order from a wallet at the prepay discount and moves it to verified. cancel releases an open order and refunds it if it had been paid from the wallet. Both are idempotent. 

{"order":{...},"price_minor":150000,"discount_minor":7500,"charged_minor":142500,"balance":357500}

POST /api/webhooks/{method}

The only inbound payment path. The adapter verifies the provider signature before anything is mutated; a failure is 401 and is logged. Full per-rail setup: webhook setup. 

{"matched":true,"order_id":"ord_...","reason":"matched","credited":true}
{"matched":false,"reason":"no_open_order","credited":false}
{"ok":true,"duplicate":true}

Reasons: matched, duplicate_txn_ref, ambiguous_amount, order_expired, no_open_order, method_mismatch.

Health and readiness

EndpointQuestionWire it to
GET /api/healthzis the process serving? (does not fail on the database)restart policy
GET /api/readyzcan it serve payments? (503 when the DB is gone)load balancer

Keeping them apart stops a missing disk from causing a restart loop, and a wedged process from staying in rotation. Verified: closing the database gives readyz 503 while healthz stays 200.

Rate limits

Per client IP, per route class. A refusal is 429 with Retry-After.

ClassEndpointsPer minuteBurst
orders_writePOST /api/orders1010
orders_readGET /api/orders/{id}12040
orders_actionclaim, cancel208
webhooksPOST /api/webhooks/{method}30060
walletwallet endpoints3010
admin/api/admin/*205

Webhooks are deliberately generous: providers retry, and throttling a real payment is worse than absorbing a burst. Behind a proxy set PB_TRUST_PROXY=1, or every request looks like the proxy and one noisy client throttles everyone.
