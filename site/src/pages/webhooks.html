Webhook setup

Every payment enters paisabridge the same way: one HTTP POST carrying one payment fact. What changes per rail is the signature scheme and whether the match may fulfil an order on its own. This page is the setup guide for each rail, in the order most deployments need them.

The rule that decides everything

If the party that sent the webhook could have forged it, the match is evidence, not proof: the order goes to review and a human confirms it. Only a signature the sender cannot mint without the shared secret may fulfil an order automatically.

The two directions

Inbound — rail → gateway

POST /api/webhooks/{method} proves a payment arrived. Configure it wherever the money lands: a bank-alert relay, the provider dashboard, or a chain watcher.

Outbound — gateway → storefront

PB_OUTBOUND_WEBHOOK_URL tells your site that an order changed state. Signed with X-PB-Signature, retried, and parked in a dead-letter table if your site is down.

The signed envelope

Rails that arrive through a relay (bank alerts, a USDT watcher, a provider whose callback has no offline-verifiable signature) speak one envelope so the gateway has a single thing to authenticate before it looks at the payload: 

{
  "id": "ntc-IBFT-001",
  "method": "bank",
  "issued_at": 1761700000,
  "payload": {
    "txn_ref": "IBFT-001",
    "amount_minor": 150700,
    "currency": "PKR",
    "sender_name": "Ali Raza",
    "received_at": "2026-10-31T08:15:00Z",
    "note": "Rs 1507.00 has been credited to A/C 12345678901234 from Ali Raza"
  }
}

The transport signature covers the id, the rail, the timestamp and the payload:

X-Paisabridge-Signature: v1=hex(HMAC-SHA256(secret,
      "v1." + id + "." + method + "." + issued_at + "." + payloadBytes))
Do not hand-assemble this JSON

The signature covers exact bytes, and any re-serialisation reorders keys and breaks it. Use the bundled CLI (or notice.Encode) to mint one: 

go build -o pbsend ./cmd/pbsend

./pbsend -url http://localhost:8080/api/webhooks/bank \
         -secret "$PB_BANK_RELAY_SECRET" -method bank \
         -amount 150700 -txn IBFT-001 \
         -sender "Ali Raza" -sender-account 12345678901234 \
         -note "Rs 1507.00 has been credited to A/C 12345678901234 from Ali Raza"
HTTP 200
{"matched":true,"order_id":"ord_9e75...","reason":"matched","credited":true}

Re-sending the same envelope is refused with replayed envelope id — the durable replay guard keeps the id, so a retry can never credit twice.

Bank IBFT / Raast (e-mail or SMS alert)

Pakistani banks do not expose a merchant API for plain account transfers, so the credit alert is the payment fact. The alert is unsigned, which is exactly why this rail never auto-fulfils.

1. Give the gateway a secret

export PB_BANK_RELAY_SECRET="$(openssl rand -hex 32)"

2. Point your alert relay at the webhook

Whatever already receives the credit alert — a Gmail filter, a Postmark inbound webhook, an SMS forwarder — POSTs the alert text to a tiny relay you control. The relay parses nothing: it wraps the text in the envelope, signs it, and forwards it. 

POST https://your-shop.example/pb-relay/bank-alert
{
  "text": "Rs 1507.00 has been credited to A/C 12345678901234 from Ali Raza on 31-10-2026"
}

The relay then forwards a signed envelope to the gateway (see above).

3. What the gateway does with it

Amount matches an open orderOutcome
exactly one, inside its windowreview — one click approves
nonestored as an unmatched notice, visible in the console
two or more (collision)review — never guessed
order already terminalrecorded as duplicate, nothing changes
Why not auto-fulfil?

Anyone who can reach that inbox can produce a convincing credit alert. The relay's HMAC proves the alert came from your relay, not that the bank sent it — so the match is a candidate, and a human confirms against the statement.

4. Alert templates understood

Parsing is strict: HBL, Meezan, UBL, Bank Alfalah, Askari, JS and a generic IBFT/Raast shape are recognised. Anything else returns ErrUnknownTemplate — an operator adds a template; the gateway never guesses.

Easypaisa

export PB_EASYPAISA_SECRET="your-onboarding-hash-key"

Easypaisa signs the callback with merchantHashedResp: AES over transactionId&code&desc, success code 0000.

FieldWhere it comes from
merchantHashedRespthe callback query string
store id / accountyour onboarding pack
return URLpoint it at /api/webhooks/easypaisa
Known limitation, stated openly

AES-ECB is malleable. The adapter therefore also binds the ciphertext to the transaction id, and the test suite pins that binding — but a rail whose signature is weaker than an HMAC is documented as such rather than presented as equal.

JazzCash

export PB_JAZZCASH_SALT="your-integrity-salt"

JazzCash posts back the pp_ fields with pp_SecureHash: HMAC-SHA256 over the sorted pp_ parameters (excluding pp_SecureHash*), keyed with the integrity salt. 

pp_TxnRefNo=PB-7F3K2Q&pp_Amount=150700&pp_TxnCurrency=PKR&pp_ResponseCode=000
...
pp_SecureHash=3f9c...e21

The published documentation is ambiguous about how values are joined. Both conventions are accepted; the matched one is reported so a deployment can pin it after its first real callback.

NayaPay

export PB_NAYAPAY_WEBHOOK_SECRET="shared-with-nayapay"
export PB_NAYAPAY_TOKEN="merchant-api-token"
export PB_NAYAPAY_BASE_URL="https://api.nayapay.com"

NayaPay gives you a webhook secret plus a merchant status API. The API is the higher bar: the adapter can re-query the provider for a transaction instead of trusting the callback body. 

POST /api/webhooks/nayapay
X-Signature: hex(hmac_sha256(webhook_secret, raw_body))

SadaPay

export PB_SADAPAY_WEBHOOK_SECRET="shared-with-sadapay"

SadaPay callbacks carry a HMAC header and a six-digit verification code. For OTP-style products that code travels to the buyer through the Telegram bot once the order is fulfilled — never before.

Binance Pay

export PB_BINANCEPAY_SECRET="binance-pay-secret-key"

Binance's published scheme, implemented exactly:

hex(HMAC-SHA256(secret, timestamp + "\n" + nonce + "\n" + body + "\n"))
Timestamp window

Binance's own SDK uses 30 seconds. This adapter allows 5 minutes because retried callbacks are normal on slow networks, and a rejected real payment is worse than a 5-minute replay window that the nonce guard closes anyway. The certificate serial number is recorded but not validated against Binance's CA — there is no offline path to that chain.

USDT (BEP-20 / TRC-20)

export PB_BINANCEPAY_SECRET="relay-secret"
export PB_USDT_RECEIVER="0xYourReceivingAddress"
export PB_USDT_CONTRACT="0x55d398326f99059fF775485246999027B3197955"   # BEP-20
export PB_USDT_CHAIN="56"

A watcher follows the receiver address and emits one signed envelope per incoming transfer. Three facts must agree before a match: the token contract, the receiver, and the confirmation count (15 on BSC, 19 on Tron — configurable).

Verify the contract yourself before funding

The contract constants ship with the source and a comment naming where they came from. Re-confirm them against the official token page before you point real money at an address.

Payoneer

export PB_PAYONEER_SECRET="link-stamp-secret"

Payoneer has no per-transaction callback with an offline-verifiable signature, so the adapter uses a domain-separated link stamp: the payment link carries an order stamp, and the inbound envelope must present the same stamp. It is labelled as an in-house protocol in the code, not as a Payoneer signature.

Telegram bot (customer + operator channel)

The bot is a notification channel, not a webhook: it long-polls Telegram, so it needs no public URL and no inbound port. Configure it from the console (Connections) or seed it with PB_TELEGRAM_TOKEN; a token saved in the console wins on the next boot. 

TURN ON:  console → Connections → paste token → Save and start
VERIFY:   console → Send test message
BUYER:    /order <ref>          (order status and payment window)
OWNER:    /start                (subscribe the chat to order events)
PropertyDetail
Transportlong polling; no webhook registration, no public URL
Credentialvalidated with getMe before it is stored

OTP deliverythe OTP is sent only after the order is fulfilled

Outbound webhook → your storefront

This is how your site learns an order was paid without polling. 

export PB_OUTBOUND_WEBHOOK_URL="https://shop.example.com/pb/hook"
export PB_OUTBOUND_SECRET="$(openssl rand -hex 32)"
POST https://shop.example.com/pb/hook
X-PB-Event: order.fulfilled
X-PB-Delivery: order.fulfilled:ord_9e75...:fulfilled
X-PB-Signature: hex(HMAC-SHA256(secret, rawBody))

{"event":"order.fulfilled","delivery_id":"order.fulfilled:ord_...:fulfilled",
 "order":{"id":"ord_...","status":"fulfilled","amount_minor":150700,...},"attempt":1}
BehaviourDetail
Signatureverify over the exact bytes; the body is JSON you already received
IdempotencyX-PB-Delivery is stable across retries — dedupe on it
Retries5 attempts with backoff; 4xx is not retried (except 429)
Eventsorder.fulfilled, .verified, .review, .expired, .cancelled

Dead letters

If your storefront is down long enough to exhaust the retries, the delivery is parked with the exact signed body instead of being lost. When your site is back: 

curl -s -H "X-Admin-Token: $PB_ADMIN_TOKEN" \
  localhost:8080/api/admin/deadletters

curl -s -X POST -H "X-Admin-Token: $PB_ADMIN_TOKEN" \
  localhost:8080/api/admin/deadletters/dl_9a2e.../retry

A retry re-sends the stored bytes, so the receiver's own signature check still passes. Verified end to end: a parking receiver produced one row after five attempts, and the retry resolved it once the receiver recovered.

Testing a rail without a provider

pbsend is the same code path the relay uses: it builds the envelope with notice.Encode, signs it, and posts it. That means a full payment can be exercised on a laptop, and the signature you test is the signature production sees.
